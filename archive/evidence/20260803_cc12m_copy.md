## The same-region proof (what the job actually asserted, on Borg)

From `_SUCCESS`:

```json
"cell": "go",                    "cell_source": "$BORG_CELL",
"bucket_region": "us-east5",
"bucket_region_proved_by": "live bigstore metadata for /bigstore/kmh-gcp-us-east5"
```

**ASSERT 2 used the strong form** — the bucket's region was read live from
`gfile.Stat('/bigstore/kmh-gcp-us-east5', stat_proto=True).blob_v2_bucket.location`
(the field `//cloud/bigstore/testing/clients/gfile_client.py` reads for
`METADATA.LOCATION`). It was NOT inferred from the bucket name. Name-matching
exists only as a fallback for when the metadata is unreachable, and it says so
in the log when it fires.

A bucket Stat is a metadata op: it moves no object bytes, so it is safe to
issue before the region is proven, and it is the only way to prove it from
inside the job.

Both asserts run before the first open and exit non-zero on unknown as well as
wrong. All five paths exercised locally before submit:

| Case | Expected | Got |
|---|---|---|
| no `$BORG_CELL` | exit 2 | exit 2 |
| `BORG_CELL=yucbfsr` (cbf/us-central1) | exit 3 | exit 3 |
| `BORG_CELL=yucmhcg` — right metro, wrong cell | exit 3 | **exit 3** |
| region forced to `us-central1` | exit 4 | exit 4 |
| `BORG_CELL=go`, real bucket | pass | pass, read `us-east5` |

The third row is the one that matters: the probe's metro-SET test would have
ACCEPTED `yucmhcg`. The literal `cell == 'go'` rejects it.

The negative path of ASSERT 2 is covered by `--test_force_bucket_region`, which
substitutes a fake region for the queried one. It can only ever make the guard
stricter — the real value is discarded — so it cannot become a way to read the
wrong region. A guard whose failing branch has never executed is a guard you
are trusting on faith.

## Throughput

No collapse. 155 MiB/s aggregate held for the whole run; the slowest shard was
9.3 MiB/s and the fastest 24.8, which is ordinary spread, not a degraded cell.
The floor (`--min_aggregate_mibps=3`, armed after 15 min) never came close to
firing. So: `fileutil quota qiaos go-d` reporting "no such user or group"
did NOT cost us a performance floor on this run — but that is one observation,
not a commitment, and the next run should still measure.

## Resume / idempotency

Not exercised: the job finished on the first attempt with no preemption. The
mechanism (BulkStat the destination, skip anything already at the correct size)
is covered by `--selftest`, which plants a stale wrong-sized destination file
and asserts it gets recopied while correct ones are skipped. Re-running the
binary now would skip all 300.

## Infra fix made along the way

`~/work/tpu_cmd` commit 388b5cc adds `--ram_gib`. The launcher built
JobRequirements from the accelerator string alone, so there was no way to ask
for RAM: `--tpu_type=cpu=4,ram=8` parses as a SECOND accelerator (one executor
per comma-separated entry), not a second resource. Default 0 omits `ram`
entirely, so every existing job keeps exactly the behaviour it had. This job
ran with `--ram_gib=12` against 8 threads x 32 MiB of copy buffer.

## Reusable pieces

- `--dry_run`   — exits before the asserts; proves imports resolve and `main()`
                  is reached. Costs seconds, catches the entire "died before
                  main()" class that is undiagnosable on Borg.
- `--guard_only`— runs both asserts and exits 0. Metadata ops only, so it is
                  safe from a workstation outside the bucket region. This is
                  how ASSERT 2 was validated before paying for packaging.
- `--selftest`  — exercises the copy engine CNS->CNS (inflight rename, size
                  verification, stale-destination recopy, resume skip,
                  throughput accounting) touching no /bigstore path.

## Known limitation

Application logs were not readable from the workstation: both
`borg tasklog` and `analog --remote` fail with
`PERMISSION_DENIED ... go/loas-restricted-credentials`. The destination
directory, the manifest, and `_SUCCESS` were the evidence instead — which is
the more durable evidence anyway, since it outlives the task. Worth knowing
before designing a job whose only output is a log line.
