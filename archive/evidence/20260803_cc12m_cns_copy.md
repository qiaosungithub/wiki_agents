## The thing that would have failed the job

**Colossus quota is charged on DISK bytes, after replication — and the default
encoding did not fit.**

- `r=3.2` (the cell default) measures **3.0166x**. 199.19 GiB of payload costs
  **600.9 GiB** of disk against a **500 GiB** per-user HDD limit.
- This is not hypothetical. The PREVIOUS job wrote this same payload to `go-d`
  at `r=3.2`, crossed the limit at 21:31Z, and **every write to `go-d` is now
  rejected**: `Poisoned file handle: "qiaos" is over Colossus bytes HDD quota`.
  Reads are unaffected, which is the only reason this job could run at all.
- Repeating it on `yucmhcg-d` would have stranded the replica at **~81%** and
  poisoned the destination cell for every other job of this user.

`rs=9.4` (Reed-Solomon, 9 data + 4 code) measures **1.4505x** — 288.9 GiB,
fits with 211 GiB to spare — and is **more** durable than 3-way replication
(survives 4 simultaneous chunk losses vs 2). Verified on a real 943 MB shard
with crc32c identical to source before committing to it.

Two measured facts that changed the design:

- **`gfile.Copy` does NOT inherit a directory's default encoding.** A plain
  Copy into an `rs=9.4` directory still produced an `r=3.2` file. Directory
  inheritance is invisible state a re-run in a fresh directory would silently
  lose, so the encoding is named per file via
  `options.open_file.stat.encoding` and read back afterwards. It survives the
  `.inflight` -> `Rename` dance.
- **RS pads small files hard.** The 152 `_stats.json` sidecars cost
  800,030,720 B of disk for 1,384,702 B of data — **578x**. Irrelevant here
  (0.75 GiB against a 211 GiB margin) but it would dominate a directory that
  was mostly small files.

`rs=10.4` was proposed and **rejected**: it is absent from the user-facing
golden list in `//file/xfile/g3doc/parameters.md` (L36-41). It appears instead
in the system's *stable* encodings — the set Colossus force-downgrades data
ONTO — which is why it looks available. It would have saved 9 GiB out of an
already-211 GiB margin.

## The guard (four literal asserts + a canary, all fail-closed, pre-read)

Adapted from `~/work/wiki_agents/storage.md` "Copying From A Bucket Someone
Else Pays For". That rule was written for a bucket; the shape is what carries
over — explicit literal asserts in the PROGRAM, before the first byte, with
unknown treated the same as wrong.

| | assert | exit |
|---|---|---|
| 0 | no `/bigstore/`, no `gs://`, every path is `/cns/` | 7 |
| 1 | Borg cell is literally `go` | 2 unknown / 3 wrong |
| 2 | source cell `go-d` metro is literally `cmh` | 4 |
| 3 | dest cell `yucmhcg-d` metro is literally `cmh` | 4 |
| 4 | payload x amplification < cell HDD quota | 8 |
| canary | one real object copied and stat'ed, encoding honoured | 9 |

Metros are **queried live** from the machine-locality client (the same data
`mach_locality -k metro` reads), not inferred from what a cell name looks like.

**Every branch was exercised locally before submit — 14 cases, all matching:**
pass; no `BORG_CELL`; wrong cell; right-metro-wrong-cell (`yucmhcg`, the case a
metro-SET test would have accepted); wrong metro on each end separately;
unreadable metro for each of the three cells separately; `/bigstore/`, `gs://`
and non-CNS paths; and the `r=3.2` budget case. Test hooks are fail-closed by
construction — `--test_force_amplification` is ignored unless it makes the
estimate *worse*, so it cannot smuggle an oversized copy past its own guard.

## Why no /bigstore path is reachable, structurally

`//cloud/bigstore/util:bigstore_file_register` is **deliberately absent** from
the BUILD deps, and `blaze query deps()` confirms nothing bigstore is linked.
Without that target a `/bigstore/` path is not resolvable at all — it is an
ordinary POSIX path that does not exist. The string checks are the loud,
diagnosable layer; the missing dependency is the layer that holds even if the
checks are edited away. `_SUCCESS` records `bigstore_paths_used: 0` over 757
distinct checked paths.

## Verification, independent of the job

The job verifies itself, but its own report is not evidence. Separately, from
the workstation:

- listing diff: all 302 source names present at the destination, nothing missing;
- **size AND crc32c compared for all 300 payload objects: 0 mismatches**,
  byte totals equal at exactly 213,877,792,915;
- destination encodings: `rs=9.4:sl=72M:bl=1M:ql=4K` x 300;
- 0 `.inflight` leftovers.

crc32c matters more than size here: the quota check runs on **every
OpenStripe**, not just `open()`, so an over-quota copy dies *mid-file* at a
stripe boundary. Size alone cannot distinguish a truncated object from a good
one — the `.inflight` -> verify -> `Rename` discipline is what makes a torn
write impossible to mistake for a finished shard.

still poisoned. The only thing on it is this dataset (199.19 GiB logical /
601 GiB disk at `r=3.2`); everything else is ~18 MB. Options: delete the `go-d`

drops.
